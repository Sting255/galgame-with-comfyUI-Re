## 二、关键设计（为什么这样做）

### 2.1 `enforceSceneFootwear`：写库 + 读取**两处**都过
提示词只能保证"大概率对"。PR#24 实测存量 15 套居家里 2 套裸脚、3 套自相矛盾（`barefoot + 拖鞋`）。
所以：
- 写库前过一遍 → 新数据干净；
- `listSceneOutfits` 读出时也过一遍 → **存量脏数据零迁移**即刻修好。

按逗号**分段原位**替换，不删关键词（会留 `covered in` 这种悬空片段），也不把拖鞋挪到末尾（会打乱结构）。

### 2.2 体型行：注册表叶子避免三角环
`characterBuild → outfitScene → characterPersona`，若 `characterPersona` 再静态 import `characterBuild` 就成环（本仓 TDZ 踩过）。
所以新增零依赖的 `bodyBuildRegistry.js`，`characterBuild` 加载期注册，`app.js` 副作用 import 一次。
实测：import 前 `BEFORE_HAS_BODY: false` → import 后 `AFTER_HAS_BODY: true`。

### 2.3 84 体位：不碰既有 17 条 / 28 条
PR#24 的 84 条 key 用 `pr24.<编号>.<actKey>`，`knowledgeId = pose.pr24.*`（PR#24 硬约束）；
本地面板精选的 17 条 `PREFERRED_POSITION_KEYS` 与 28 条 `TOUCH_ACTIONS` **逐字不动**（测试断言条数与首尾项）。
分类用标签而非 prompt 判插入：84 条里 60 多条 prompt 会提到 penis（哪怕乳交），只看 prompt 会判成 78/84 插入（明显错）。

### 2.4 生图等待预算：不改 SSE 协议的最小解法
以前 `await imageGenPromise` **无限等**，ComfyUI 慢时整条流不收尾 → 用户观感「卡住半天，突然一堆」。
现在给上限（默认 20s）：
- 图在预算内完成 → 行为与以前**完全一致**；
- 超预算 → 打 warn 先收尾，任务继续在后台跑（`send` 有 `res.writableEnded` 保护，不会抛错）。
