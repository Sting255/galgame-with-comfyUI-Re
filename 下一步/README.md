## 一、直接结论

**当前项目具备可继续开发的真实基础，但不能认定为“整体没问题”，也不建议按现状直接发布。**

前端能构建、后端内存库能启动、保留回归测试可运行，主要业务也并非空壳。真正需要优先处理的是：

1. **消息与发布正确性**：群聊流可永久等待，App 重复挂载会重复订阅；多处后台内容在生成后没有重新检查角色状态。
2. **移动与信任边界**：Android 原生通知没有携带配对凭证，原生桥对所有加载页面开放；源码中还有不应交付的凭据。
3. **备份与恢复语义**：数据库本身包含部分密钥，但“无配置备份”文案容易误导；恢复后的向量索引没有可靠的强制重建代际。
4. **发布链可复现性**：两套发布入口语义不同，根发布命令调用了启动器不支持的参数；旧签名私钥仍可随 Git 历史传播。
5. **异步任务生命周期**：延期不等于自动续跑，部分 `processing/generating` 在重启后无人接管，失败分片可能被当作完成。
6. **UI 基座一致性**：已有 Linshe 组件体系，不需要重做视觉；要修的是漏接弹窗、键盘操作、流状态和大型页面的职责边界。

### 发布判断

**结论：暂缓发布，先完成 P0 与发布验收。**

P0 在此定义为“发布或核心正确性阻断”，不是安全 CVSS 评分。依赖告警也按实际可达性另行判断，不能直接把 `npm audit` 的严重级别当作本应用已遭利用的证据。

### 不建议做的事

- 不重写全部前后端，不迁移到微服务，不为了“架构先进”引入消息队列或 Kubernetes。
- 不做一次全站换肤，不用大面积格式化掩盖行为错误。
- 不把所有带 `town` 字样的代码直接删除；部分组件仍被聊天、事件和背包使用。
- 不把静态检查、空库截图、ComfyUI 不在线的退出码 2 当成完整验收。
- 不继续为每个调度器各写一套 try/catch、内存 Map 和“启动时恢复”。

## 四、后续开发必须遵守的架构原则

1. **SQLite 是业务真源，Chroma 是可重建派生物，文件是独立资产。** 不用数据库字段假装外部生成一定完成，不把 Chroma 当备份真源。
2. **用户操作与后台自动化不是同一授权语义。** 手动生成、历史补发、被点名回复可以有例外；纯后台公开必须在每次公开前检查角色存在、系统作用域、睡眠与功能开关。
3. **“生成、落库、公开、完成”是不同事件。** 任何异步任务都需要持久终态与幂等键，不能只在入口处检查一次。
4. **所有任务都有归属、超时、取消与恢复。** `AbortController`、流取消和数据库任务状态必须能对应起来，不能只停在 UI 的 spinner。
5. **单实例是明确约束，不是偶然事实。** 所有调度器只能有一个持有者；将来扩展先实现租约，不可直接多开后端。
6. **密钥绝不进入源码、公开 Git 历史或“无凭据”备份。** 文档不保存真实密钥，测试不读取玩家 `.env`。
7. **UI 只改基座与职责，不改设计语言。** Linshe 组件、暖纸/暗夜 tokens 和 300ms 过渡是既有约束；先修键盘与焦点，再谈视觉。
8. **一个发布入口、一棵干净源码树、一个版本。** 源码、前端产物、运行时、启动器、APK 和校验清单必须来自同一提交。

## 五、推荐执行顺序

```text
第一批：撤销/替换公开凭据 → 修 Android 配对与原生桥 → 修备份秘密文案/语义
   ↓
第二批：群聊超时与取消 → App SSE 退订 → JSON 完整性与身份锚点真源
   ↓
第三批：评论/回复/媒体/离线的幂等与恢复 → 统一公开前闸门
   ↓
第四批：统一发布入口与依赖升级 → CI 执行保留测试 → 干净包与 Android 实测
   ↓
第五批：朋友圈服务端分页 → 弹窗/键盘基座 → 按业务域拆巨型页面
```

不要把这个顺序倒过来。先消除数据与安全风险，再做结构优化，才能用回归测试保护后续重构。
