# 02｜目标架构与模块设计

> 目标：在不推翻现有产品的前提下，把“多模块能运行”收敛为“同一事实、同一任务生命周期、同一设备边界、同一发布路径”。  
> 本文描述施工后的目标形态；当前差异见 `01-问题台账.md`。

## 1. 总体技术决策

### 保留

- Windows 单机/受信 LAN 为主，Node.js + Express 作为唯一业务入口。
- Vue 3 + Pinia + Router，构建产物由后端托管；Vite 仅开发使用。
- SQLite 单主库、WAL、本地图片/音频资产；Chroma 仅作派生向量索引。
- ComfyUI/NovelAI 生图、LLM 网关、Python 向量服务、可选 IndexTTS adapter。
- Windows 启动器与 Android WebView 壳；现有暖纸/暗夜 UI 体系。
- 单用户、单后端实例、单调度持有者的部署模型。

### 不做

- 不引入微服务、数据库集群、Kafka/RabbitMQ、独立用户系统或服务端 SSR。
- 不让 Python 服务直接持有业务写入权限；不开放公网管理接口。
- 不把“后台任务”简单替换成一堆 setInterval，也不把 Chroma 当作必须迁移的数据。

### 原因

这个项目的复杂度主要来自 LLM/生图的长耗时与副作用，不是请求吞吐量。增加分布式组件只会多出新的状态真源。当前最短路径是：**一个业务主库 + 持久任务协议 + 有界资源队列 + 可重建索引 + 一条发布链**。

## 2. 当前与目标部署图

```text
┌──────────────────── Windows 主机 ────────────────────┐
│ Windows Launcher                                    │
│  └─ 进程/端口/运行时/日志/升级（只管理，不复制业务规则） │

│ Browser / Android WebView                           │
│        │ HTTPS 或显式受信 LAN HTTP                  │
│        ▼                                            │

│  ├─ Access & Origin & Device Identity               │
│  ├─ HTTP API / SSE / Static UI & Assets             │
│  ├─ Character / Chat / Social / Media / Diary ...   │
│  ├─ Publish Gate / Character Scope / Persona        │
│  ├─ Persistent Jobs & Schedulers                    │
│  ├─ LLM Client / Outbound HTTP / GPU Queue          │
│  └─ SQLite + backup/restore journal                 │
│        │                     │                      │
│        ▼                     ▼                      │
│  Vector Service          TTS Adapter                │
│  127.0.0.1 + provider    127.0.0.1 + random token  │
│  可重建索引               可选、受托管生命周期         │
│        │                     │                      │
│        └────── External Providers ─────────────────┤
│             LLM / Embedding / ComfyUI / NovelAI     │
└─────────────────────────────────────────────────────┘

Android Native SSE ──独立可撤销 Device Token──> agent-core
Android Native Bridge ──仅 approvedOrigin──────> 保存/上传等能力
```

### 进程边界

1. `agent-core` 是业务写入唯一入口，路由不得把密钥或无鉴权内部服务暴露到 LAN。
2. `vector-service` 只接受回环，支持本地/远端 embedding profile 的索引与查询；不能凭 `/health` 推断索引正确。
3. `tts-service` 是可选 adapter，随机服务 Token、受托管生命周期、与 ComfyUI 共享有界 GPU 资源。
4. Launcher 只负责运行时与进程，不再另写一套数据迁移/版本语义。
5. ComfyUI 是外部执行器；本地任务放弃不等于远端任务取消，必须记录 promptId 和终态。

## 3. 后端分层与职责

```text
routes / maibot-bridge
    │ 输入验证、HTTP 状态、用户明确操作语义
    ▼
application services
    │ 角色作用域、用例编排、幂等键、任务创建
    ├───────────────┬──────────────────┐
    ▼               ▼                  ▼
domain policies   persistent jobs    provider adapters
publish gate      claim/retry/lease  LLM / Comfy / TTS / Embedding
sleep/scope       cancel/recover     timeout/cancel/body limit
    │               │                  │
    └───────────────┴────────┬─────────┘
                             ▼
                     SQLite + filesystem
```

### Routes

- 只解析参数、鉴权、调用应用服务、映射错误；不直接拼接多步公开流程。
- 所有 `async` handler 统一异常处理；请求断连不是业务取消的充分条件，是否取消由用例决定。
- 路径挂载顺序必须保留明确契约，新增 `/:id` 通配前检查已有子路由。
- 成功响应只表示“已接收”“草稿完成”或“已公开”中的一种，不能混用 `ok:true`。

### Domain policies

- `characterScope.USER_SCOPE`：面向用户集合唯一作用域；按 ID 单体与显式点名保留现有例外。
- `scheduleManager.isSleeping()`：睡眠唯一判定点，禁止业务层手写时间比较。
- `publishGate.checkCharacterPublishable()`：公开前存在性、系统角色、睡眠、功能开关的统一判定。
- `characterPersona`：生图人格唯一拼装入口；`imageSkill._execute` 统一身份锚点注入。
- 手动用户操作、被点名、后台自动任务分用例传参，不能为“统一”而误拦用户明确行为。

### Provider adapters

统一 `executeWithDeadline` 语义：

- 超时覆盖 DNS/连接、响应头、响应体与取消，不只是一个包裹 `fetch()` 调用的 timer。
- 下载流式限制字节数；结构化错误包含 provider、operation、retryable、requestId，不包含密钥。
- 所有可重试请求需要幂等策略；LLM 生成“已发出但未收到结果”不能盲目重复计费。
- TLS 配置限制在具体 provider client，不修改进程级证书校验。

## 4. 数据真源与一致性

| 数据 | 真源 | 派生/缓存 | 恢复原则 |
|---|---|---|---|
| 角色、人设、身份锚点 | SQLite characters | 提示词中的人格/外观拼装 | 身份与身体只改锚点；manual 不被自动覆盖 |
| 聊天、群聊、评论 | SQLite raw/messages 等 | Pinia、SSE 播放队列 | 消息 ID 去重，流可恢复但不重复 |
| 日程、睡眠 | 日程状态与统一管理器 | 角色缓存睡眠字段 | 公开前实时判定，不从旧缓存猜 |
| 媒体/日记/信箱 | SQLite 草稿与公开字段 | 图片、前端列表 | 草稿、素材、公开、终态分列 |
| 记忆 | SQLite fragments/triples | Chroma collections | 恢复代际强制 stale，按当前 provider 重建 |
| 图片/音频 | 文件内容 + DB 引用 | AVIF 回退、浏览器缓存 | 快照或合并语义必须显式，文件清理可重试 |
| 配置 | DB settings/profiles + .env | 进程内 config | 秘密分类，不用文件名判断是否含 Key |
| 任务 | SQLite 任务与副作用关联 | 内存 promise/timer | 启动按所有权恢复，不靠内存 Map |

### SQLite 迁移

1. 引入 `PRAGMA user_version`，每版单向迁移，记录 app/schema version。
2. 每个结构迁移在 `BEGIN IMMEDIATE` 内执行；seed 与结构分开，重复执行需幂等。
3. 启动先备份/校验迁移能力，失败不继续跑调度器；不能“打印 error 后带病启动”。
4. 设置 busy_timeout，明确 synchronous；WAL 不是事务和备份的替代品。
5. 角色删除等用例在一个事务处理数据库，文件删除进入提交后的清理队列。
6. 备份 manifest 加 `appVersion/schemaVersion/providerMetadata/secretClasses`，只写元数据不写秘密。

## 5. 统一任务协议

### 不立即建一张“大而全”的表

现有 `reply_queue`、`moment_comment_queue`、`photo_studio_jobs`、`character_diaries` 等有领域字段。先用公共模块和小字段收敛，不一次重写所有调度器。逐步统一以下字段语义：

```text
id / job_type / owner_key / idempotency_key
status = pending | claimed | deferred | succeeded | failed | cancelled | discarded
attempt / max_attempts / next_attempt_at / lease_until
input_snapshot / draft_snapshot / provider_reference
result_reference / error_code / error_detail
created_at / updated_at / completed_at
```

不要求每个领域表物理列完全相同，但状态含义、认领/恢复/取消函数必须一致。

### 状态机

```text
pending ──原子认领──> claimed ──成功且副作用确认──> succeeded
   ▲                   │  ├─可重试错误──> pending(next_attempt_at)
   │                   │  ├─角色睡眠/开关──> deferred(next_attempt_at)
   │                   │  ├─用户取消/角色删除──> cancelled/discarded
   │                   │  └─永久失败──> failed（可见原因）
   │                   └─进程消失/lease 到期──> 安全恢复
   └──────── deferred 到期且条件满足
```

### 必须遵守的规则

1. **入口检查 + 每次公开前检查**：LLM/生图之后角色状态可能已经变化。
2. **认领、业务副作用、任务完成在一个事务中可核对**：外部生成不能放进 SQLite 事务，采用“素材已暂存→公开事务→完成”两段式。
3. **幂等键在数据库唯一**：例如 `(character_id,user_comment_id)`、`offline:chunk:<range>`、`media:<postId>`；应用层先查再插不算原子幂等。
4. **discard 是终态**：查询、认领、写回和完成回调都必须拒绝复活。
5. **延期必须有驱动**：retry_at + 低频扫描/唤醒事件；返回 deferred 本身不算完成。
6. **恢复先证明没有仍在执行的持有者**：单实例启动时可回收；定时 tick 不得重置正在生成的长任务。
7. **失败不能清游标**：离线分片有未决项就不能完成整轮。
8. **已暂存外部素材可复用**：角色醒来不应无意义重烧已成功的图片。

### 建议模块

`agent-core/src/services/jobs/` 下逐步提供：

- `claimJob.js`：原子认领与租约。
- `retryPolicy.js`：可重试、延期、终态分类与退避。
- `recoverJobs.js`：启动恢复清单，只执行一次。
- `publishTransaction.js`：公开前闸门 + 副作用落库 + 完成证明。
- `jobEvents.js`：统一进度/终态 SSE，不携带秘密或大字段。

先迁移评论队列、媒体 feed、回复队列、离线补偿，再覆盖日记/特殊日程；不要先写一个没人使用的大框架。

## 6. 流式消息与前端状态

### API 层

- 普通请求统一 `requestJson`；流统一 `openStreamResponse + consumeSSE`，包括连接、首事件、无活动与总任务 deadline。
- 返回 `{ stream, abort, completed }` 或等价契约，store 必须保存 abort，不得丢弃。
- HTTP 401、403、网络失败、JSON 错误、远端失败和主动取消是不同状态。
- 取消只改变本地等待；需要后端取消时发送明确轮次/任务 ID。

### Store 层

- sending 按 conversation/group，不用一个全局布尔值拖死所有会话。
- 每个异步操作带 `requestGeneration + entityId`；返回时验证仍属于当前对象。
- 乐观消息有 `local/sending/sent/failed`，失败可重试，不能只留一个永久用户气泡。
- SSE handler 注册返回退订函数；App/视图卸载必须全部退订；消息 ID 去重作为兜底。
- 流断开后通过持久消息恢复，不能只靠 Toast；已收到的内容只追加、不伪造“重新生成”。

### UI 基座

- `LinsheButton/Input/Select/Switch/Tabs/Modal` 是唯一常规控件；白名单仅保留确有独立交互的输入与热区。
- Modal 统一焦点圈、Escape 栈、标题关联、300ms 进出场、after-leave 卸载；抽屉可保留外形但复用基座行为。
- Select 支持 ArrowUp/Down/Home/End/Enter/Escape 与 active descendant；一级导航使用 router-link。
- 主题只用 tokens；不新增第三套皮肤。组件 accessibility 修复不改变布局。

## 7. 设备身份与网络安全

### 目标模型

- 根配对码只用于一次性配对，不作为永久设备 Bearer。
- 每台设备有独立 `device_id + device_token + created_at + last_used_at + revoked_at`。
- Web Cookie 保持 HttpOnly/SameSite=Strict，HTTPS 下 Secure；原生 SSE 用设备 Bearer。
- 支持“撤销单台设备”和“轮换全部设备”；UI 显示真实有效期，不把 Cookie 30 天说成根配对码 30 天。
- 本机 loopback 的便利保留，但不能信任 Forwarded 头或任意外站 origin。
- 受信 LAN HTTP 是明确便利模式，不能宣称公网安全；公网/不可信网络必须 HTTPS。

### Android

- approvedOrigin 存在受保护配置；导航/重定向/iframe 与 JS Bridge 都检查它。
- 原生 Token 用 Keystore 加密，排除自动备份；401 停止通知重连并引导重新配对。
- 不在 URL、通知正文、日志、普通 JS localStorage 中保存设备秘密。
- 后台通知需单独验收电池策略、厂商 ROM、重启和切网，不承诺所有 ROM 永久在线。

## 8. 备份、恢复与迁移

### 备份分类

1. **业务数据**：SQLite + 图片/音频/头像；默认即可包含，但提示数据库可能有秘密。
2. **运行配置**：非秘密端口、模型名、provider URL、尺寸等。
3. **秘密**：LLM/TTS/NovelAI/Vertex/embedding/MaiBot/device tokens 等，必须显式选择。
4. **派生数据**：Chroma、可再生成缓存不打包，恢复后重建。

### 恢复事务

```text
上传并校验 tar/manifest/hash/路径
  → 停止写入与调度，生成当前快照
  → 持久化 restore journal（phase=prepared）
  → staging 解包与 SQLite 完整性检查
  → 替换 DB/按所选模式替换或合并资产（journal 记录每一步）
  → 设置 restore_generation，active 记忆标 stale
  → 提交并重启
  → 启动检测未完成 journal：优先回滚或安全续做
  → 向量 worker 重建，UI 显示进度/错误
```

“快照替换”和“合并”只能选一种明确展示；Launcher 换机迁移复用同一核心，不再直接复制后宣告成功。

## 9. 前端性能与模块边界

### 先做有收益的优化

- 朋友圈分页与筛选下推，避免首屏最多 50 个顺序请求。
- 长列表服务端分页/虚拟化；视口外图片 lazy/async。
- 保持路由懒加载；用实际网络/profile 决定是否再拆首屏 vendor。
- 消除重复 SSE handler、无效轮询和过期请求，比压缩几十 KB 更重要。

### 拆分原则

按业务域而不是按“模板/样式/script 各一个文件”：

```text
features/chat/{api,store,composables,components}
features/groups/{api,store,composables,components}
features/settings/{llm,image,memory,backup,access}
features/media/{api,store,components}
shared/ui/Linshe*
shared/stream/{client,subscriptionScope}
shared/jobs/{status,retryView}
```

不必一次移动所有文件。先在原目录抽 composable/业务 API，调用方稳定后再移动，避免无收益的大范围 import diff。

## 10. 发布与版本架构

唯一事实源：一个精确版本标签对应一棵干净提交树。

```text
clean commit + exact tag
  → npm ci / locked Python & Android dependencies
  → backend/TTS tests + imports + frontend lint/build
  → launcher build & self-test
  → optional Android build/lint/sign (signing outside public tree)
  → sanitized release source/export without sensitive history
  → image smoke (must exit 0 for release)
  → desktop/mobile UI screenshots
  → clean-directory install/start/backup/restore
  → manifest/SBOM/checksums/release candidate
```

- `VERSION`、launcher 内嵌版本、包元数据、发布 tag 由同一工具派生，不分别手改。
- `scripts/发布-校验并打包.mjs` 可保留为门禁库，但不能与根 release 各维护一套版本/文件规则。
- 发布包不得包含 `.env`、launcher_config、签名材料、玩家 data、浏览器会话、敏感 Git objects。
- 依赖升级与功能修复分开提交；真机验收不通过不发布。
